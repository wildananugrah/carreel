Three implementation approaches

All three use TF.js on-device + bounding boxes + hints for Gemini. The difference is which model and how inference is triggered.

A

EfficientDet-lite0 — Recommended ✦

Train EfficientDet-lite0 on the public CarDD dataset (Kaggle), convert to TF.js format, serve from /public/models/. Run inference on a 320×240 canvas frame every 1.5s during recording. WebGL backend (~30–50ms/frame), WASM fallback for devices without GPU support.

Pros

  • ~4.4MB model — fast to load, fits in memory
  • No network calls during recording
  • Works offline / in tunnels
  • Easy to swap in fine-tuned model later (just replace the files)

Cons

  • Needs one-time training run in Python (Keras + TF)
  • Accuracy limited by small model size on subtle damage
B

MobileNet-SSD (COCO pre-trained) + re-head

Use the @tensorflow-models/coco-ssd npm package (already has a TF.js-ready MobileNet-SSD) and replace only the detection head with a custom 3-class head (dent / scratch / intact) fine-tuned on CarDD. Faster to ship since the base model is downloadable via npm, no conversion step.

Pros

  • Base weights available as npm package — no conversion needed
  • ~6MB, well-tested on mobile browsers
  • Fastest path to a working demo

Cons

  • Slightly larger than EfficientDet-lite0
  • Fine-tuning the head still requires a Python step
  • Slightly lower accuracy than EfficientDet on small objects
C

Hybrid: TF.js trigger → Gemini frame confirm

Use a tiny 1–2MB binary classifier (dent present? yes/no) running every 2s. When it fires, capture the frame and send it to the backend where Gemini analyzeImage() returns the actual bounding box + label. The bounding box shown on screen comes from Gemini, not TF.js.

Pros

  • Bounding box accuracy = Gemini quality
  • Tiny on-device model (~1MB)
  • No training needed for the localisation step

Cons

  • Needs network during recording — fails in poor signal
  • Adds Gemini API cost per detected frame (~10–30 frames/inspection)
  • 0.5–2s delay before box appears on screen (round-trip)
  • More moving parts (backend endpoint + streaming response)

Performance budget — mid-range Android

All three run inference on a 320×240 downscaled canvas (not the full 720p camera feed) and throttle to 1 frame per 1.5s. This keeps CPU usage under ~15% on a Snapdragon 680 / Helio G85. Full 720p inference would take 5–10× longer and heat the device.
